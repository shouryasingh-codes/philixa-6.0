### 6.3 Technical Interview Defense Playbook
When evaluated by Senior Engineers, Shourya must deliver crisp, confident answers to these 6 core architectural challenges:

#### Q1: "How do you enforce safe NL-to-SQL without prompt injection or tenant data leakage?"
> **Defense:** *"We implement a defense-in-depth pipeline: First, the LLM-generated SQL query is parsed into an Abstract Syntax Tree (AST) using `sqlglot`. We restrict AST operations strictly to `SELECT` statements (blocking `DROP`, `UPDATE`, `INSERT`, `ALTER`). Second, the AST automatically injects a mandatory `WHERE tenant_id = :current_user_tenant_id` clause before execution. Finally, the query runs against PostgreSQL using a restricted, read-only database role."*

#### Q2: "How does the Redis WebSocket ticket replay guard work?"
> **Defense:** *"Because browsers cannot send custom headers during native WebSocket handshakes, authenticating via URL tokens risks leakage in server logs. We use a two-step handshake: The client requests a short-lived, single-use ticket (TTL 60s) via an authenticated HTTPS endpoint. When opening the WebSocket, the client passes this ticket. The backend executes an atomic Redis `GETDEL` operation. If the key exists, the connection upgrades and the ticket is instantly destroyed, preventing replay attacks. If the key is missing or expired, the handshake is aborted with HTTP 4401."*

#### Q3: "Why use browser AudioWorklet for 16kHz Int16 PCM streaming instead of standard MediaRecorder?"
> **Defense:** *"The standard `MediaRecorder` API produces compressed container formats (WebM/Opus) in large time chunks (1–2s), which introduces latency and forces the backend to run CPU-intensive audio decoding. ASR models like Whisper require uncompressed 16kHz 16-bit linear PCM. By using an `AudioWorkletProcessor` on the browser's dedicated audio rendering thread, we capture raw 128-sample frames, downsample from hardware sample rate (e.g. 48kHz) to 16kHz via linear interpolation, convert Float32 `[-1.0, 1.0]` to Int16 `[-32768, 32767]`, and stream binary chunks over the WebSocket with under 50ms latency."*

#### Q4: "Why choose BAAI/bge-m3 and how is pgvector indexed for 1024 dimensions?"
> **Defense:** *"We chose `BAAI/bge-m3` because it provides state-of-the-art multi-lingual retrieval and 1024-dimension dense representations. In PostgreSQL, we index vector embeddings using HNSW (`pgvector`) with Cosine distance (`vector_cosine_ops`), configuring `m=16` and `ef_construction=64`. This gives sub-20ms approximate nearest neighbor search while avoiding the recall degradation associated with IVFFlat on dynamic datasets."*

#### Q5: "How did you measure the ~70% LLM cost reduction and >98% schema compliance?"
> **Defense:** *"In baseline testing, 100% of user CRM queries were routed to GPT-4o. In production, our StateGraph router evaluates incoming requests against deterministic regex matchers for common CRM CRUD commands (e.g., client lookups, status updates, note creation). This intercepts ~68% of standard traffic with zero LLM token consumption. For the remaining generative queries, we enforce Pydantic v2 schema validation with fallback self-correction loops, achieving >98% first-pass schema compliance across automated evaluation suites."*

#### Q6: "Why ARQ over Celery for background workers?"
> **Defense:** *"Celery is heavy, relies on synchronous workers, and introduces friction when integrated with `asyncio` event loops in FastAPI. ARQ is built natively on Python's `asyncio` and `redis-py`, allowing our background workers (cron sweeps, WhatsApp dispatches, audio transcript processing) to share the same asynchronous non-blocking paradigms as our API layer with minimal memory footprint."*
